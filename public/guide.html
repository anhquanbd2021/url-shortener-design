Lab guide

Redirect first, count afterwards — and mint codes you never have to check

The whole service compresses to one sentence. Each panel below maps a lab feature to the claim it proves — and the production failure mode it makes visible before production does.

A model, not a deployment. The store, cache, browser cache, and queue are in-memory stand-ins; latencies are representative constants. The lab makes the article's claims legible — it does not serve real traffic.

The lab features

What each decision proves

Minting

A counter beats dice

Shorten 200 links with the counter strategy — zero collision lookups, because a monotonic counter encoded in base62 is unique by construction. Switch to random draw, enable rig collisions, and watch extra SELECT round trips pile up before every insert.

Proves
Code generation is the real design question: counter + base62 gives uniqueness for free; random draws buy a mandatory collision check on every write, forever.
Key detail
7 base62 chars span 62⁷ ≈ 3.5 trillion codes — ~17× what a busy service mints in a decade. Hashing the URL itself is the interview anti-pattern: two users, same URL, same code.
Read path

A redirect is one cache read

Fire 100 clicks with 90% aimed at one hot link. The cache absorbs the skew and the database only serves cold misses — the trace shows hit vs miss hop by hop.

Proves
Click traffic is power-law skewed — roughly 1% of links carry over 90% of clicks — so a tiny hot set in RAM sees >99% hit rates.
Key detail
Cache-aside done right: miss → SELECT → populate → redirect. Every miss makes the next hit free; skipping the layer "because Postgres is fast" turns the first viral moment into pool exhaustion.
Analytics

After the redirect, never inside it

Compare 100 clicks each way. An inline INSERT INTO clicks adds a full DB write to every redirect; a queued event adds ~0 ms and still counts every click.

Proves
The most-copied shortener diagram is wrong: analytics inside the read path makes redirect latency a database write — hundreds of ms at p99 under contention.
Key detail
The fix is ordering, not omission: publish {code, ts, referrer, ua, ip} to a queue, return the 302 immediately, let a consumer count asynchronously. The user is already gone.
Status code

301 is a one-way door

Send 10 repeat clicks per status. With 301, one click is counted and nine resolve inside the browser cache — the server never sees them. With 302, all ten arrive.

Proves
301 Moved Permanently tells the browser to cache the redirect — possibly forever. The dashboard reads zero while the links work fine: the article's 9:15 incident.
Key detail
With 301 you also lose the ability to edit the destination or kill the link — the browser won't ask. Default to 302/307; choose 301 only when losing the traffic is the goal.
Real HTTP

The same model over the wire

Section five drives the server, not the page: POST /api/shorten mints a code, and the generated /r/:code link returns a real 301/302 redirect with a queued click event.

Proves
The mechanisms are not just a simulation — the browser and the test suite exercise the same domain model the server runs.
Key detail
Open a ?status=301 link twice in the same browser: the second request may never leave it. No cookie, no request log — the click simply never exists.
